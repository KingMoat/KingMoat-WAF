# CRS 异常评分机制说明（Anomaly Scoring）

KingMoat WAF 的签名检测内核由 Coraza 引擎与内嵌的 OWASP CRS（Core Rule Set）规则集构成，采用 CRS 官方的「异常评分（Anomaly Scoring）」模式：规则命中不直接拦截，而是按严重级别累计异常分，累计分达到阈值才阻断。本文说明这套机制的计分规则、阈值语义与调优方法，供处置误拦、评估拦截效果时参考。

| 文档信息 | |
|---|---|
| 机制基线 | OWASP CRS 异常评分模式（计分与阈值语义遵循 CRS 官方默认） |
| 相关配置 | `policy.inbound_threshold` / `policy.outbound_threshold`，字段说明见 [CONFIG.md](CONFIG.md) |
| 控制台入口 | 策略管理 → CRS 异常评分阈值 |

## 1. 机制总览

一次请求在 CRS 检测中的评分与阻断流程：

```
规则命中（按严重级别记分）──▶ 累计异常分 ──▶ 阻断评分规则比较阈值 ──▶ 达标阻断 / 未达标放行
```

- **计分**：每条 CRS 检测规则命中时，按其严重级别（severity）对应的分值给当次请求累计异常分。
- **评估**：入站评分在请求检测完成时由入站阻断评分规则（CRS 规则 949110）评估，出站评分在响应检测完成时由出站阻断评分规则（CRS 规则 959100）评估——累计分达到阈值即阻断（默认 403 拦截页）。
- **隔离**：入站分与出站分分别累计、分别比较，互不叠加。

## 2. 计分表

| 严重级别 | 分值 | 典型来源 |
|---|---|---|
| CRITICAL | 5 | 应用攻击类规则（SQL 注入、XSS、RCE、LFI/RFI 等） |
| ERROR | 4 | 出站信息泄露类规则 |
| WARNING | 3 | 恶意客户端类规则 |
| NOTICE | 2 | 协议合规类规则 |

分值为 OWASP CRS 官方默认语义，由 CRS 规则集自带的初始化规则定义（`tx.critical_anomaly_score` 等变量），KingMoat 未做修改；「典型来源」一列同为 CRS 官方对该类规则的分类描述。

## 3. 累计语义

- 累计分 = 该请求命中的全部 CRS 规则的分值之和。
- 单条规则对评分的最大贡献等于其严重级别对应的分值：同一规则无论命中多少处，只按其严重级别记一次分（CRS 语义）。
- 示例：一次请求命中 1 条 CRITICAL（+5）与 2 条 WARNING（+3、+3），入站累计分为 11。

## 4. 阈值：入站与出站

| 参数 | 配置字段 | 默认值 | 控制台范围 | 含义 |
|---|---|---|---|---|
| 入站异常评分阈值 | `policy.inbound_threshold` | 5 | 1–100 | 请求侧累计分达到该值即阻断 |
| 出站异常评分阈值 | `policy.outbound_threshold` | 4 | 1–100 | 响应侧累计分达到该值即阻断 |

- 默认值下，入站 1 条 CRITICAL 命中、出站 1 条 ERROR 命中即达阈值——与 CRS 官方默认行为一致。
- 1–100 为控制台输入范围限制；字段值未配置或为 0 时按默认值（5 / 4）处理。
- 修改后经控制台「保存并发布」热生效，无需重启服务。

### 调优方向

阈值调高更宽松（减少误拦）、调低更严格（更早阻断）。OWASP CRS 官方在 `crs-setup.conf.example` 的调优说明中给出的参考量级：

- **7**：需要多条规则命中累计才能阻断；
- **10**：约两条 CRITICAL 告警或大量低级别告警的组合才会阻断；
- **新部署渐进策略**：初始可使用远高于默认值的阈值（或配合站点「观察模式」）上线，观察日志后逐步调低到目标值。

官方同时明确警示：阈值超过 5（入站）/ 4（出站）后，LFI、RFI、RCE 与数据泄露等防护能力会逐步失效——高于默认值仅建议作为误报调优的**临时**手段，长期运行应回到「精确加白」而非「抬高阈值」。

## 5. 防护等级（Paranoia Level）

CRS 的防护等级（PL1–PL4）决定规则集的启用深度：等级越高，参与检测的规则越多、越严格，误报也越多。

- KingMoat 当前固定 **PL1**（CRS 默认等级），未对外暴露 PL2+ 配置。PL1 下全部 CRITICAL 级应用攻击规则均生效，是检测覆盖与误报的均衡起点。
- PL2+ 会额外启用更激进的规则（针对非常规参数、编码变形等场景），通常需要配合精细化加白使用。后续版本如开放 PL2+，本文档将同步更新。

## 6. 与 KingMoat 实现的关联

| 环节 | 行为 |
|---|---|
| 阈值注入 | 引擎为站点构建 WAF 时，把两个阈值写入 CRS setup 变量（`tx.inbound_anomaly_score_threshold` / `tx.outbound_anomaly_score_threshold`），并固定 PL1 |
| 配置字段 | `policy.inbound_threshold` / `policy.outbound_threshold`，控制台发布后热生效 |
| 分类关闭 | 站点级 `waf.categories` 裁剪或微引擎 `coraza:<分类>` disable 关闭的 CRS 分类不参与检测，自然不再计分 |
| 微引擎 allow / 一键加白 | 微引擎放行规则（含攻击日志页「一键加白」生成的规则）命中后，请求跳过 CRS 检测，不再产生评分 |
| 审计归因 | 阻断由评分规则触发时，攻击日志的「命中规则」归因为累计分数的具体攻击规则（如 942100 → SQL 注入），原因字段保留全部命中规则明细 |

## 7. 调优指南：误拦处置

出现误拦时，按以下优先级处置（影响范围从小到大）：

1. **精确加白（优先）**：从攻击日志对具体请求一键加白（站点 + 路径条件的放行规则），或为已知合法业务特征（扫描器来源、含特殊参数的接口）添加微引擎放行规则。只影响匹配的请求，防护能力不缩水。
2. **调高阈值（次选，临时）**：误拦面广且暂无法逐条加白时，临时调高阈值（如 5 → 7）。注意官方警示：高于默认值会逐步失去整类防护，加白完成后应调回。
3. **关闭分类（最后）**：确认某类检测（如 `php`）与业务完全无关时，在站点级关闭该分类。该分类内全部规则不再参与检测与评分，影响面最大，需评估后使用。

## 8. 排查方法

1. 控制台「攻击日志」定位被拦请求：结果为拦截、状态 403，「命中规则」列显示归因后的攻击规则标识（如 `coraza/rule-942100`）。
2. 命中规则与评分明细：审计事件的 `reason` 字段列出该请求全部命中规则（规则 ID + 消息），其中阻断评分规则的消息携带当次总评分（`Total Score: N`）；可通过日志导出接口（`GET /api/logs/export`，NDJSON）获取完整字段。
3. 结合计分表核对各命中规则严重级别对应的分值，确认累计分与阈值的差距，再按第 7 节选择处置方式。
